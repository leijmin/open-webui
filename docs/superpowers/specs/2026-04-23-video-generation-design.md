# 胡椒文旅视频生成接入设计

## 背景

当前 `胡椒文旅` 站点已经完成品牌化改造，并且图片生成链路已经能够正常工作。站点底层仍基于 `Open WebUI v0.8.10`，聊天能力、文件存储、消息附件展示和文件预览能力均已可用。

本次目标是在不破坏现有聊天主流程的前提下，为站点增加“视频生成”能力，并保持老板视角下的简单易用：

- 用户像发一条消息一样发起视频生成
- 生成过程尽量中文、直白、少技术术语
- 成功后直接在聊天中看到可播放的视频结果

## 当前现状

### 已有能力

- 前端聊天消息已经支持展示 `video/*` 类型文件
- 文件预览页已经支持 `<video>` 播放
- 后端已有成熟的图片生成链路：
  - 配置读取与更新
  - 模型识别
  - 结果下载
  - 结果写入文件存储
  - 结果挂载到聊天消息
- 当前上游 `https://yunwu.ai/v1` 已经通过现有 OpenAI 外接配置接入，并且模型列表中存在多种视频模型

### 已确认的上游视频模型样本

- `veo3.1-fast`
- `veo3.1`
- `sora-2-pro`
- `viduq3-pro`
- `wan2.5-i2v-preview`

这些模型的 `model_type` 多为 `音视频`，`supported_endpoint_types` 中包含：

- `视频统一格式`
- `openAI官方视频格式`
- `vidu文生视频`
- `vidu图生视频`
- `wan视频生成`

这说明当前接入的视频能力不是概念验证，而是可以基于现有供应商继续扩展。

## 目标

1. 支持在聊天中发起文生视频
2. 支持在聊天中发起图生视频
3. 支持视频生成任务的异步状态轮询
4. 成功后把视频结果落入现有文件系统，并作为聊天附件展示
5. 在普通用户视角中保持简单、中文、少参数
6. 保持管理员可配置默认视频模型和上游视频配置

## 非目标

- 不在本次实现中支持首尾帧、视频延长、角色一致性、数字人等高级模式
- 不在本次实现中支持多图生视频
- 不做复杂的专业级视频参数面板
- 不重构现有聊天架构和消息存储结构
- 不替换当前上游供应商

## 方案选择

### 方案 A：仅做文生视频

优点：

- 实现最快
- 交互最简单
- 风险最小

缺点：

- 无法满足图生视频场景
- 用户需要后续再次迭代

### 方案 B：文生视频 + 图生视频

优点：

- 覆盖最常见的业务需求
- 仍然能保持交互边界清晰
- 与当前聊天上传图片能力天然兼容

缺点：

- 需要补充“图片参考输入”的后端适配
- 异步任务和结果处理比文生视频更复杂

### 方案 C：一次性把高级视频能力全部接入

优点：

- 功能最全

缺点：

- 上游差异大，适配复杂
- 前端交互容易迅速膨胀
- 老板视角下会显得过于技术化
- 首版风险明显偏高

### 结论

采用 **方案 B：文生视频 + 图生视频**。

原因：

- 覆盖核心业务场景
- 在不增加太多复杂度的情况下，具备较高展示价值
- 能复用现有图片上传、文件存储和聊天附件能力

## 用户体验设计

### 1. 聊天输入区

在聊天输入区增加一个 `视频生成` 开关，层级与当前 `图片生成`、`联网搜索`、`代码解释器` 保持一致。

交互规则：

- 用户选中支持视频生成的模型时，按钮可用
- 用户选中视频专用模型时，默认自动点亮 `视频生成`
- 用户切回纯文本对话模型时，按钮自动关闭
- `视频生成` 与 `图片生成` 不同时开启，避免同一条消息意图冲突

### 2. 文生视频模式

用户直接输入提示词并发送，例如：

- “生成一段夜晚洛阳古城灯会的视频”
- “生成一段赛博朋克风格的小猫视频”

系统行为：

- 识别为视频生成请求
- 发起异步任务
- 在聊天中显示状态提示
- 完成后直接显示视频播放器

### 3. 图生视频模式

用户先上传一张图片，再打开 `视频生成` 并发送描述，例如：

- 上传景区海报后输入“让画面里的人物缓慢转头并微笑”

第一版仅支持：

- 1 张图片作为参考图

超出范围时：

- 多图场景直接提示“当前仅支持一张参考图片生成视频”

### 4. 生成状态文案

状态文案统一中文化，不暴露技术任务细节：

- `正在提交视频任务`
- `视频生成中，请稍候`
- `正在获取视频结果`
- `视频已生成`
- `视频生成失败，请稍后重试`

### 5. 结果展示

成功后：

- 结果视频作为聊天附件挂到当前助手消息
- 消息区直接渲染视频播放器
- 文件预览区继续复用现有视频预览能力

失败后：

- 助手消息给出中文失败说明
- 不展示任务 ID、原始供应商字段名或未处理的接口报文

## 技术设计

### 1. 前端结构

#### 需要扩展的能力

- 新增视频生成开关状态
- 新增“当前模型是否支持视频生成”的能力识别
- 在发送消息时把 `video_generation` 作为功能标记传给后端
- 在消息事件流里接收视频文件附件并展示

#### 主要改动点

- `src/lib/components/chat/Chat.svelte`
  - 默认功能识别
  - 视频模型自动点亮逻辑
- `src/lib/components/chat/MessageInput.svelte`
  - 视频生成按钮
  - 图生视频输入约束
- `src/lib/stores/index.ts`
  - 前端配置类型增加视频开关
- `src/lib/constants/permissions.ts`
  - 权限常量增加 `video_generation`
- `src/lib/utils/`
  - 新增视频模型能力识别工具

### 2. 后端结构

#### 新增路由

新增独立视频路由：

- `backend/open_webui/routers/videos.py`

提供接口：

- `GET /api/v1/videos/config`
- `POST /api/v1/videos/config/update`
- `GET /api/v1/videos/models`
- `POST /api/v1/videos/generations`
- `GET /api/v1/videos/tasks/{task_id}`

#### 新增配置

视频配置与图片配置分离，避免互相污染。建议新增持久化配置：

- `ENABLE_VIDEO_GENERATION`
- `VIDEO_GENERATION_ENGINE`
- `VIDEO_GENERATION_MODEL`
- `VIDEOS_OPENAI_API_BASE_URL`
- `VIDEOS_OPENAI_API_KEY`
- `VIDEOS_OPENAI_API_VERSION`
- `VIDEOS_OPENAI_API_PARAMS`

第一版默认：

- engine 使用 `openai`
- base URL / key 默认可从现有 OpenAI 外接配置继承，但允许在视频配置中单独覆盖

#### 新增中间层处理

在聊天中间件中补一条与图片类似的视频处理链：

- `chat_video_generation_handler(...)`

触发条件：

- `features.video_generation === true`

该处理器负责：

1. 从当前消息提取文本提示词
2. 检查是否存在 1 张参考图片
3. 调用视频生成接口
4. 轮询任务状态
5. 下载最终视频文件
6. 存入现有文件系统
7. 通过事件流把视频文件挂给当前助手消息

### 3. 上游适配层

这是本次设计的核心。

由于当前供应商虽然通过 OpenAI 风格统一接入，但视频模型的任务提交、轮询和结果格式未必与图片完全一致，因此需要一个统一的适配层。

建议新增：

- `backend/open_webui/utils/videos/`
  - `providers.py`
  - `models.py`
  - `normalizers.py`

职责：

- 屏蔽供应商字段差异
- 统一任务创建响应
- 统一任务轮询状态
- 统一结果视频 URL 抽取
- 统一错误信息

对聊天层暴露的统一结构建议为：

- 创建任务后返回：
  - `task_id`
  - `status`
- 轮询状态返回：
  - `queued`
  - `running`
  - `succeeded`
  - `failed`
- 成功时返回：
  - `video_url`
  - `content_type`
  - `metadata`

### 4. 文件入库

成功拿到视频结果后，不直接把外链裸露给前端，而是复用现有文件上传与存储能力：

1. 下载上游视频二进制
2. 写入 `Storage`
3. 使用现有 `Files` 记录文件元数据
4. 以站内 `/api/v1/files/{id}/content` URL 作为最终展示地址

这样做的收益：

- 前端无需适配外部临时 URL 失效问题
- 权限控制继续沿用站内文件逻辑
- 文件预览和聊天消息展示无需额外改造

### 5. 模型能力识别

前后端都需要补充 `video_generation` 能力识别。

第一版识别规则：

- `model_type` 为 `音视频`
- 且 `supported_endpoint_types` 中包含以下任一特征：
  - `视频`
  - `文生视频`
  - `图生视频`
  - `视频统一格式`
  - `openAI视频格式`

对于纯视频模型：

- 默认自动开启 `video_generation`

对于同时具备多模态理解但非视频生成模型：

- 不自动开启，只保留普通对话能力

## 数据流

### 文生视频

1. 用户选择视频模型
2. 前端自动点亮 `视频生成`
3. 用户输入提示词并发送
4. 前端在请求 `features` 中传递 `video_generation: true`
5. 后端聊天中间件进入 `chat_video_generation_handler`
6. 后端调用上游创建视频任务
7. 后端轮询任务直到完成或失败
8. 成功后下载视频文件
9. 后端存入站内文件系统
10. 后端通过事件流把视频附件发送给聊天消息
11. 前端直接渲染视频播放器

### 图生视频

1. 用户上传 1 张图片
2. 用户选择支持视频的模型
3. 打开 `视频生成`
4. 用户输入动态描述并发送
5. 后端提取参考图 URL 或文件内容
6. 调用上游图生视频接口
7. 其余流程与文生视频一致

## 错误处理

### 用户输入错误

- 未输入提示词：阻止发送并提示中文说明
- 图生视频上传了多张图：阻止发送并提示仅支持 1 张
- 参考图格式不支持：提示更换图片

### 模型或配置错误

- 未开启视频生成：提示管理员开启视频功能
- 默认视频模型为空：提示管理员配置默认模型
- 当前模型不支持视频生成：前端按钮不可用，发送时兜底报错

### 上游任务错误

- 提交失败：直接返回中文失败信息
- 轮询超时：提示“视频生成时间较长，请稍后再试”
- 结果下载失败：提示“视频已生成，但获取结果失败，请重新生成”

### 存储错误

- 文件写入失败：提示“视频生成成功，但保存失败”

## 默认策略

第一版默认视频模型建议使用：

- `veo3.1-fast`

原因：

- 从当前模型描述看，适合文生视频和首版展示
- 相对更强调速度和性价比
- 更适合作为老板视角演示的默认入口

## 实施顺序

1. 补充视频生成配置、权限和前端配置类型
2. 增加视频模型能力识别
3. 新增视频路由与视频适配层
4. 新增聊天视频处理中间链路
5. 前端加入视频生成功能入口
6. 接入文生视频
7. 接入图生视频
8. 补充中文状态与错误提示
9. 本地验证
10. 视结果决定是否上线

## 风险与处理

### 风险 1：上游视频接口是异步且返回结构不统一

处理：

- 在后端增加统一适配层
- 前端只认内部稳定状态格式

### 风险 2：视频生成耗时明显长于图片生成

处理：

- 明确提供生成中状态
- 轮询使用超时与退避策略，避免前端疯狂请求

### 风险 3：图生视频的图片输入格式要求不一致

处理：

- 第一版只支持单图
- 后端统一把站内图片文件转换为上游所需格式

### 风险 4：结果视频外链失效

处理：

- 不依赖外链长期展示
- 一律下载并保存到站内文件系统后再展示

## 验收标准

- 用户能够在聊天中发起文生视频
- 用户能够上传 1 张图并发起图生视频
- 生成过程显示中文状态
- 成功后聊天消息中能直接播放视频
- 管理员可以配置默认视频模型
- 视频结果通过站内文件系统提供，不直接依赖外链
- 失败时显示可理解的中文错误说明
